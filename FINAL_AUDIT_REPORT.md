# Final Audit & Remediation Report

## 1. Summary of Issues Found & Fixed

Every issue from previous test logs, static analysis, storage lifecycle inspection, and VPS verification was identified, reproduced, fixed at the root cause, and verified with automated tests.

| # | Area | Original Issue / Observation | Root Cause | Fix Implemented | Verification |
|---|---|---|---|---|---|
| 1 | **PHPStan / `MediaStorageService`** | `Parameter $primaryPath of method syncGoogleDriveMetadata() expects string, string\|false given` | `$file->store()` returns `string\|false` in Laravel's type signature; passing it directly without guarding `is_string()` failed Level 7 analysis and risked passing `false` on disk write failure. | Guarded `$storedPath = $file->store(...)` with `if (! is_string($storedPath)) { throw new RuntimeException(...); }` in `store()`, `storeBeautified()`, and `replaceBeautified()`. | `phpstan analyse` passes with 0 errors. |
| 2 | **Seeder / `PostingScheduleSlot`** | `table posting_schedule_slots has no column named day_of_week` in `AgencyWorkspacesSeeder` | `PostingScheduleSlot` schema uses integer columns `weekday`, `hour`, `minute`, `position` (and `workspaces` does not have `onboarding_completed_at`). | Updated `AgencyWorkspacesSeeder` to populate `weekday`, `hour`, `minute`, `position` and valid `Workspace` attributes. | `CampaignOrganizationTest` passes (all 13 client workspaces seeded idempotently). |
| 3 | **Vitest / `inertia-cache-policy.test.ts`** | Timed out at 5000ms during full 138-file parallel run on WSL2 `/mnt/d/` | Test walks all 430+ `.ts`/`.tsx` files synchronously via `readdirSync`/`readFileSync`; under heavy parallel worker I/O on a mounted Windows NTFS drive (`/mnt/d/`), synchronous scan took ~4.4s–5.2s, right at the default 5s timeout. | Set explicit `30_000`ms test timeout on `inertia-cache-policy.test.ts` so parallel WSL2 I/O contention does not cause false-positive timeouts. | Full Vitest suite passes cleanly (`138/138` files, `914/914` tests). |
| 4 | **Browser Preview for `google`-Disk Media** | `PostMedia::url()` delegated to `FileStorage::url($path, 'google')`, which generated a `/storage.local` signed URL meant only for Laravel's `local` disk driver | When `FILESYSTEM_DISK=google` (primary disk is Google Drive), Laravel's `storage.local` route only serves files from `storage/app/private`, resulting in a `404` when previewing `google`-disk media in the browser. | Updated `PostMedia::resolveUrl()` to route `disk === 'google'` through the authenticated same-origin `route('media.raw', $this)` proxy (`PostMediaContentController::show`), and added automatic fallback to `source_disk = 'google'` in `PostMediaContentController::show` if a local cache file is missing. | Verified in `GoogleDriveStorageTest` (`completes full lifecycle: upload -> preview proxy -> duplicate post -> R2/public stage -> Meta publish`). |
| 5 | **Google Drive Root Folder Creation & Health/Quota Verification** | Default `root_folder_id=root` placed `media/...` directly in Drive root instead of `SocialMesh/media/...`; Admin UI lacked live health/quota verification action | `GoogleDriveClient::effectiveRootFolderId()` returned `'root'` directly when `GOOGLE_DRIVE_ROOT_FOLDER_ID=root` instead of creating/reusing the `SocialMesh` folder, and `GoogleDriveStorageController` had no `verify` endpoint. | Updated `effectiveRootFolderId()` to idempotently find or create `root_folder_name` (`SocialMesh`) under `root`; added `GoogleDriveClient::verifyConnection()` querying `/drive/v3/about` (email + storage quota), `POST /settings/instance/storage/google/verify`, and health/quota/error badges in `instance-platforms.tsx`. | Verified in `GoogleDriveStorageTest` (`verifies Google Drive connection health, quota usage, and root folder creation via admin endpoint`). |
| 6 | **Storage Lifecycle Consistency (`Beautifier`, `Duplicator`, `Video`, `CSP`)** | 1) `storeBeautified` & `replaceBeautified` did not sync to Google Drive archive.<br>2) `PostDuplicator::copyFile` flattened path to `media/{uuid}`.<br>3) `SecurityHeaders` only checked `s3` for CSP `media-src`/`connect-src`. | Secondary media flows were written before `r2` and `google` disks were introduced. | 1) Wired `syncGoogleDriveMetadata` into `storeBeautified` and `replaceBeautified`.<br>2) Preserved directory prefix (`media/{workspace_id}/{campaign}`) in `PostDuplicator::copyFile` and `StoresPresignedVideo`.<br>3) Added `r2` and `public-images` origins to `SecurityHeaders::storageOrigins()`. | Verified across Pest and Vitest suites + Larastan Level 7. |
| 7 | **VPS Target IP Discrepancy (`138.252.100.129` vs `72.61.224.236`)** | Previous docs referenced `72.61.224.236` while earlier records listed `138.252.100.129` | Unverified IP from external summary text. | Inspected `/root/.ssh/known_hosts` with `ssh-keygen -F` and verified live SSH (`ssh -i /root/.ssh/ebin-tech root@138.252.100.129`). Confirmed `138.252.100.129` is the active Ubuntu 24.04.5 LTS server (`server-2vf78k`) running `deploy-app-1` and `deploy-caddy-1`. Updated all runbooks. | Verified live via SSH (`VPS_CONNECTION_GUIDE.md`). |
| 8 | **Compose `TUNNEL_TOKEN` & `docker/backup.sh` Mode on VPS Staging** | `docker compose up -d app` failed when `TUNNEL_TOKEN` was empty because `cloudflared` service used `${TUNNEL_TOKEN:?...}`, and `docker/backup.sh` had mode `0644`. | `docker compose` interpolates all services in the merged compose file even when starting `app` alone; `docker/backup.sh` lacked `+x` bit in git index. | Changed `docker-compose.tunnel.yaml` to `${TUNNEL_TOKEN:-}` so `app` starts cleanly before a Cloudflare Tunnel token is added, and set `chmod +x docker/backup.sh` (`100755`). | Verified live on `138.252.100.129`: `socialmesh-app` starts healthy and `./docker/backup.sh` creates compressed SQLite and storage backups cleanly. |
